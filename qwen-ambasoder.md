# Qwen Ambassador Application

## "Is there any project you are currently working on that you believe has strong potential? Please share a brief overview with us."

I'm currently building an **AI-assisted traffic accident detection and emergency dispatch system** as my final-year university project, and it's the project I'd point to.

**The problem:** road accidents in resource-constrained settings (my context is Ghana) often go unreported for critical minutes — no bystander calls it in, or there's no reliable connectivity to do so. The system watches live or recorded traffic camera footage, recognizes when an accident has actually happened, and automatically alerts emergency contacts by SMS and voice call, with no human needing to watch a screen.

**Why it's more than a toy demo:**

- **Two-stage detection gate.** A fast object detector (DETR) flags any frame that could plausibly be an accident, but a single detector alone is unreliable — strict enough to avoid false alarms and it misses real accidents; loose enough to catch them and it fires on ordinary traffic. So every flagged frame gets a second, careful visual check from a vision-language model before anything is dispatched. **Qwen2.5-VL (3B, run fully locally via Ollama) is that second stage** — it out-performed every other offline model I benchmarked head-to-head (including a larger Qwen3-VL variant and Gemma), reaching 77.8% accuracy / 66.7% recall / 100% precision on a hand-labelled 9-item calibration set, and remained the only offline model with zero hangs or timeouts at pipeline scale on a full 54-item set. It's the model that makes the offline path viable at all.
- **Offline-first by design, not as an afterthought.** The central goal is a pipeline — detection, verification, *and* alerting — that needs no internet connection at any stage, because that's the actual deployment constraint in the environments this is meant to serve. SMS and calls route through a repurposed Android phone acting as its own gateway over a normal SIM, not a cloud API.
- **Rigorously evaluated, not just built.** I assembled and hand-labelled a 54-frame test set, benchmarked candidate models against each other, and directly compared the detector alone vs. the full hybrid pipeline at multiple confidence thresholds — the hybrid raised precision from 60% to 86.7% at the deployed setting, a measurable, documented improvement, not a vibes-based claim.

**What's next — a custom, fully offline accident-scene explainer.** Right now the verifier only answers yes/no (is this an accident?) plus a short templated alert. The next stage of the project is to go further: **SFT fine-tune Qwen2.5(-VL) on accident-scene imagery** so it can produce a fuller, more useful explanation of what a responder is about to walk into — what's involved, how severe it looks, what's blocking the road — still running fully offline, still small enough to run on modest local hardware. The goal is a model that doesn't just gate an alert, but genuinely helps under-resourced, low-connectivity communities get better information faster, before anyone with more capacity arrives on scene.

**Why I think it has strong potential — beyond the technical results:** my supervisor took me to demo the system to **Kumasi Metropolitan Assembly (KMA) members**, and it led to a real discussion about piloting it on specific intersections within the city. That's the part that makes this feel like more than a class project to me — a local government body engaging seriously with the idea of an actual rollout. I'm also planning to **publish a paper on this as an undergraduate**, built around the fine-tuned explainer model and the evaluation work already done.

That combination — a compact, locally-run vision-language model carrying real decision-making weight in a safety-critical loop, validated with real municipal stakeholders, and headed toward a published, fine-tuned model rather than stopping at a class demo — is what I'd want to champion as a Qwen ambassador: Qwen models doing real work offline, on modest hardware, for communities cloud-first AI tooling tends to leave out.

## "Anything else we should know?"

A couple of things about where I'm coming from that I think are relevant:

- **I'm building this from and for the environment it's meant to serve.** I'm an undergraduate at KNUST in Kumasi, Ghana — the same city where this project is being piloted — so the offline-first constraint isn't a hypothetical design goal for me, it's the actual condition I'm building and testing under. That's also why I care specifically about Qwen: it's one of the few open-weight model families where a 3B vision-language model is genuinely capable enough to be trusted in a real decision loop, which is what makes local, offline deployment viable at all on the hardware people here actually have.
- **This will be my first published paper, written while still an undergraduate.** I don't have a research track record yet — this project is meant to be the start of one. If accepted as an ambassador, I'd want to use that platform honestly: sharing what fine-tuning and deploying Qwen on real, messy, low-resource-context data actually looks like, including the parts that don't work (the DETR-only vs. hybrid trade-offs and offline-voice-call gap documented in this project are examples of things I'd write about candidly, not just the wins).
- **I'm early-career but this project already has a path beyond the classroom** — a municipal stakeholder conversation, a planned publication, and a concrete next model to build. I'd bring that same seriousness to representing Qwen: not just using the models, but documenting and sharing what building with them in a genuinely resource-constrained setting takes.
